PostgreSQL is a powerful, open-source relational database management system known for its advanced features, extensibility, and support for complex queries and large datasets.
Read more about [PostgreSQL](https://www.postgresql.org/).

## Example Usage

Make sure you have PostgreSQL installed and configured.
Then, you can connect it straight into Better Auth.

```ts title="auth.ts"
import { betterAuth } from "better-auth";
import { Pool } from "pg";

export const auth = betterAuth({
  database: new Pool({
    connectionString: "postgres://user:password@localhost:5432/database",
  }),
});
```

<Callout>
  For more information, read Kysely's documentation to the
  [PostgresDialect](https://kysely-org.github.io/kysely-apidoc/classes/PostgresDialect.html).
</Callout>

## Joins

Database joins are useful when Better-Auth needs to fetch related data from multiple tables in a single query.
Endpoints like `/get-session`, `/get-full-organization` and many others benefit greatly from this feature,
seeing upwards of 2x to 3x performance improvements depending on database latency.

The Kysely PostgreSQL dialect supports joins out of the box since version `1.4.0`.
To enable this feature, set `advanced.database.joins` to `true` in your auth configuration.

```ts title="auth.ts"
import { betterAuth } from "better-auth";

export const auth = betterAuth({
  advanced: {
    database: {
      joins: true,
    },
  },
});
```

## Use a non-default schema

PostgreSQL uses the `public` schema by default. You can select another schema explicitly with `database.schemaName` or configure PostgreSQL's `search_path`.

When both are configured, Better Auth uses `database.schemaName`. Other unqualified queries continue to use the connection's `search_path`.

### Set `database.schemaName`

<Tabs items={["Kysely dialect", "Kysely instance"]}>
  <Tab value="Kysely dialect">
    ```ts title="auth.ts"
    import { betterAuth } from "better-auth";
    import { PostgresDialect } from "kysely";
    import { Pool } from "pg";

    export const auth = betterAuth({
      database: {
        dialect: new PostgresDialect({
          pool: new Pool({
            connectionString: "postgres://user:password@localhost:5432/database",
          }),
        }),
        type: "postgres",
        schemaName: "auth", // [!code highlight]
      },
    });
    ```
  </Tab>

  <Tab value="Kysely instance">
    ```ts title="auth.ts"
    import { betterAuth } from "better-auth";
    import { db } from "./database";

    export const auth = betterAuth({
      database: {
        db,
        type: "postgres",
        schemaName: "auth", // [!code highlight]
      },
    });
    ```
  </Tab>
</Tabs>

The schema applies to runtime queries and CLI migrations. `npx auth@latest migrate` creates it when needed and ignores same-named tables in other schemas.

`npx auth@latest generate` starts the generated migration by creating the schema:

```sql
create schema if not exists "auth";
```

All subsequent statements use schema-qualified table names, such as `"auth"."user"`.

The PostgreSQL role used by Better Auth must be able to create the schema and its tables. Otherwise, create the schema and grant access to that role before running `npx auth@latest migrate`.

### Set `search_path`

Use PostgreSQL's `search_path` instead when passing a `pg.Pool` directly, or when every unqualified query on the connection should use the same schema.

When using `search_path`, the Better Auth CLI expects the schema to already exist. Create it and grant access to the connection role before running `npx auth@latest migrate`.

<Tabs items={["Pool options", "Connection string"]}>
  <Tab value="Pool options">
    ```ts title="auth.ts"
    import { betterAuth } from "better-auth";
    import { Pool } from "pg";

    export const auth = betterAuth({
      database: new Pool({
        connectionString: "postgres://user:password@localhost:5432/database",
        options: "-c search_path=auth",
      }),
    });
    ```
  </Tab>

  <Tab value="Connection string">
    ```ts title="auth.ts"
    import { betterAuth } from "better-auth";
    import { Pool } from "pg";

    export const auth = betterAuth({
      database: new Pool({
        connectionString: "postgres://user:password@localhost:5432/database?options=-c%20search_path%3Dauth",
      }),
    });
    ```
  </Tab>
</Tabs>

To make the schema the default when a PostgreSQL role connects to a specific database:

```sql
ALTER ROLE your_role IN DATABASE your_database
SET search_path TO auth;
```

Reconnect after changing this default. Run `SHOW search_path` to verify the active value.

## Amazon Aurora DSQL

Use the separate `@better-auth/dsql-adapter` package for Aurora DSQL. It reuses Kysely's PostgreSQL operations and Better Auth's schema planner, and keeps DSQL-specific retries, SQL compilation, and index jobs in the adapter package.

Install the adapter and [AWS node-postgres connector](https://docs.aws.amazon.com/aurora-dsql/latest/userguide/SECTION_program-with-dsql-connector-for-node-postgres.html):

```sh
pnpm add @better-auth/dsql-adapter kysely pg @aws/aurora-dsql-node-postgres-connector @aws-sdk/credential-providers @aws-sdk/dsql-signer
pnpm add -D @types/pg
```

```ts title="auth.ts"
import { AuroraDSQLPool } from "@aws/aurora-dsql-node-postgres-connector";
import { dsqlAdapter, dsqlDialect } from "@better-auth/dsql-adapter";
import { betterAuth } from "better-auth";
import { Kysely } from "kysely";

const pool = new AuroraDSQLPool({
  host: process.env.DSQL_ENDPOINT!,
  user: process.env.DSQL_USER!,
  max: 3,
});

export const db = new Kysely({ dialect: dsqlDialect({ pool }) });
export const auth = betterAuth({
  database: dsqlAdapter(db),
  rateLimit: { storage: "database" },
});
```

Grant the application's IAM role access to the cluster and map it to the database user. The connector generates fresh IAM tokens when opening connections. Keep the pool outside your Lambda request handler so warm invocations reuse connections. For a non-default schema, pass the same `{ schemaName: "auth" }` to `dsqlAdapter` and `getDsqlMigrations`.

### Migrations

The adapter provides schema generation and migration hooks. Run migrations separately from application requests:

```sh
npx auth@latest migrate
```

Use `npx auth@latest generate` to inspect the SQL without applying it. You can also run migrations programmatically:

```ts title="migrate.ts"
import { getDsqlMigrations } from "@better-auth/dsql-adapter/migration";
import { auth, db } from "./auth";

try {
  const migration = await getDsqlMigrations(auth.options, db);
  await migration.runMigrations();
} finally {
  await db.destroy();
}
```

Both paths use the adapter's migration plan, which reuses the shared planner and refuses unsafe changes and schema problems. The DSQL dialect creates indexes with `CREATE INDEX ASYNC` and waits for each job on the same connection. Rerunning a migration resumes matching pending jobs and restores missing field indexes. Failed or incompatible indexes require inspection in `sys.jobs` and correction before retrying.

When applying generated SQL yourself, execute statements individually and wait for each returned job ID using `CALL sys.wait_for_job('<job_id>');` before relying on the index. See [DSQL asynchronous indexes](https://docs.aws.amazon.com/aurora-dsql/latest/userguide/working-with-create-index-async.html).

### Transactions and storage

The adapter enables transactions. A serialization abort (`40001`) retries the complete transaction, or a single adapter operation outside a transaction, up to three times with backoff. Other errors propagate immediately. Before hooks and transactional callbacks may repeat; send emails and call external services from after hooks, which run after a successful commit. Email signup uses the existing shared after-commit mechanism. Persistently contended operations can still fail after the retry limit.

String IDs remain the default. Numeric IDs (`advanced.database.generateId: "serial"`) use `bigint` identity columns with `CACHE 1`; gaps are possible. Sessions and verification records use the database without secondary storage. Rate limiting defaults to process memory without secondary storage; set `rateLimit.storage: "database"` explicitly for Lambda deployments. This adapter currently rejects `secondaryStorage`: transaction retries cannot roll back external cache writes. DSQL's SQL and transaction limits still apply to custom schemas and plugins.
